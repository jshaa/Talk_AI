## 1. Executive Summary

### 1.1 한 줄 결론
> **기술적으로는 지금 바로 만들 수 있습니다. 하지만 "카톡 대화 → 특정 인물(특히 상대방이나 고인) Persona"를 회사 서버에서 처리하는 B2C 모델은 현행 개인정보보호법과 이루다 선례 기준으로 회사를 위험하게 만드는 구조입니다.**
> 상용화가 현실적인 경로는 다음과 같습니다.
> ① **완전 로컬(Local-only), 회사는 데이터를 받지 않음**
> ② **본인 발화 중심(Self Persona) 또는 본인 동의를 받은 인물(Creator, 직원 다수 집계)만 Persona화**
> ③ **상대방 데이터는 "맥락"으로만 쓰고 모델링·학습 대상에서는 제외**
> ④ **고인 Persona는 생전 동의(Digital Legacy)가 있을 때만**

### 1.2 왜 위험한가 (핵심 4가지)
1. **상대방(대화 상대) 개인정보에는 처리 근거가 거의 없습니다.** 업로드한 사용자 A의 동의는 상대방 B의 동의가 아닙니다. 회사가 B의 정보를 서버에서 처리하려면 개인정보 보호법 제15조의 근거가 필요합니다. 그런데 B와는 계약 관계가 없고, '정당한 이익'(제15조 제1항 제6호)은 "명백하게 정보주체의 권리보다 우선"해야 합니다. 대화 속 **민감정보(건강·정치·종교·성생활 등)는 제23조에 따라 별도 동의 또는 법령 근거가 있어야 하므로 정당한 이익으로는 처리할 수 없습니다** [S1]. **[가능성 높음]**
2. **이루다 선례가 있습니다.** 스캐터랩은 '연애의 과학' 이용자가 넣은 카톡 대화를 챗봇 학습과 응답 DB에 썼다가, 2021년 PIPC에서 과징금·과태료 합계 약 1억 330만 원 처분을 받았습니다. 처리방침의 "신규 서비스 개발" 문구만으로는 이용자가 예상할 수 없었다는 이유입니다 [S6]. 2025년 7월 서울동부지법 1심도 위자료 배상 책임을 인정했습니다(1인 10만~40만 원) [S7]. 이 사업과 사실관계가 거의 같습니다.
3. **Persona의 목적 자체가 "특정 개인의 재현"입니다.** 그래서 가명처리·익명화로 면책받는 구조(제28조의2, 제58조의2)와 본질적으로 맞지 않습니다. 말투 자체가 식별자입니다. **[가능성 높음]**
4. **AI 기본법(2026-01-22 시행)이 적용됩니다.** 생성형 AI 기반이라는 사전 고지와 결과물 표시 의무가 있습니다. 과태료 계도기간이 최소 1년 있으므로 실제 과태료는 빨라야 2027년 이후입니다 [S8]. **[확실]**

### 1.3 그래도 사업이 되는 이유
- **Local-first로 회사가 데이터를 전혀 받지 않으면** 회사가 대화 내용의 "개인정보처리자"가 아닐 가능성이 높습니다. 개인이 사적 목적으로 쓰는 경우에는 "업무를 목적으로"(제2조 제5호) 하는 처리가 아니어서 PIPA 적용이 제한될 여지도 있습니다. **[가능성 높음, 법률 검토 필요]** 이것이 이 사업의 가장 큰 구조적 무기입니다.
- 한국 메신저 내보내기 파일의 파싱, 한국어 구어체 스타일 모델링, 출처 기반 기억(근거 없는 기억 생성 차단)은 해외 서비스가 잘 못하는 영역입니다.
- B2B 쪽 수요(CS·영업 교육용 "표준 응대 Persona", 온프레미스)는 지불 의향이 B2C보다 훨씬 높습니다.

### 2.2 반드시 구분해야 하는 개념
| 혼동 | 왜 다른가 | 제품 설계에 미치는 영향 |
|---|---|---|
| **RAG ≠ Model Training** | RAG는 원문을 검색해 프롬프트에 **일시적으로 넣는 것**이고 모델 가중치는 바뀌지 않습니다. 학습은 데이터를 가중치에 **흡수**시킵니다. | RAG 데이터는 행 단위 삭제가 가능하지만 학습된 모델은 그렇지 않습니다. 동의 항목도 "기억 검색 허용"과 "학습 허용"으로 나눠야 합니다. |
| **Embedding ≠ 완전한 익명화** | 임베딩 역변환 공격(Vec2Text 등)으로 원문을 상당 부분 복원할 수 있다는 연구가 있습니다 [S26]. | 벡터도 원문과 같은 등급으로 암호화·삭제합니다. |
| **Masking ≠ 자동적인 법적 면책** | 마스킹은 안전조치의 하나일 뿐이고 처리 근거를 대신하지 못합니다. 맥락으로 재식별될 수 있습니다. | 마스킹 후에도 동의·국외이전 절차는 그대로 필요합니다. |
| **Local Processing ≠ 모든 법률 문제 해결** | 회사의 처리자 지위는 약해지지만 AI 기본법, 인격권, 제품 악용, 사용자 자신의 법적 책임은 남습니다. | 로컬에서도 고지·표시·악용 방지 UX가 필요합니다. |
| **KakaoTalk Export 가능 ≠ Commercial AI Use 허가** | 내보내기는 카카오가 이용자에게 주는 **편의 기능**일 뿐입니다. 약관에는 다른 이용자 정보의 무단 수집·이용·제공 금지 조항이 있습니다. | 제품명·마케팅에서 카카오와의 제휴를 암시하면 안 됩니다. |
| **Fine-tuning ≠ Memory Database** | 파인튜닝은 "어떻게 말하는가"를 학습하는 데는 적합하지만 "무엇이 있었는가"를 저장하는 데는 부적합합니다(출처·삭제·정정 불가). | 사실은 Memory DB에, 문체는 Style Profile/Adapter에 둡니다. |
| **User Upload Consent ≠ Counterparty Consent** | 동의는 정보주체 본인에게서 받아야 합니다. | 참여자별 Consent 상태 관리가 필수입니다(9장). |
| **Pseudonymization ≠ Anonymization** | 가명정보는 추가정보로 재식별할 수 있으므로 개인정보입니다. 익명정보만 법 적용에서 제외됩니다(제58조의2). | "익명화했으니 자유"라는 마케팅 문구는 금지합니다. |
| **Persona Simulation ≠ 실제 사람** | 출력은 통계적 생성물입니다. 실제 인물의 의사나 기억이 아닙니다. | 상시 표시, 근거 표시, 사칭 금지(18장)가 필요합니다. |

### 3.2 핵심 쟁점: "사용자가 자신이 참여한 카톡 대화를 업로드하면 회사가 상대방 개인정보까지 처리할 수 있는가?"

#### (1) 먼저 누가 "개인정보처리자"인가
- 개인정보처리자는 "**업무를 목적으로** 개인정보파일을 운용하기 위하여 스스로 또는 다른 사람을 통하여 개인정보를 처리하는" 자입니다(제2조 제5호) [S1].
- 시나리오별 판단:

| 시나리오 | 회사 지위 | 사용자 지위 | 판단 |
|---|---|---|---|
| S1. 완전 로컬, 회사로 아무 데이터도 가지 않음 | 소프트웨어 공급자. 대화 데이터의 처리자가 아닐 가능성 | 사적 이용이면 '업무 목적'이 아니어서 처리자가 아닐 가능성 | **[가능성 높음]** 다만 사용자의 민사 책임(인격권)은 남음 |
| S2. 로컬 + 크래시 로그/텔레메트리에 대화 일부 포함 | **처리자** | — | 텔레메트리 설계 실수 하나로 S3가 됨 |
| S3. 회사 서버에서 분석·저장·학습 | **처리자** | 정보 제공자 | 상대방 정보 처리 근거 필요 → 아래 (2) |
| S4. 사용자 본인 API 키(BYOK)로 PC에서 해외 LLM 직접 호출 | 처리자 아닐 가능성. 다만 "다른 사람을 통하여" 처리로 볼 여지, 설계 책임 | 사용자의 선택 | **[법률 검토 필요]** |
| S5. 회사 API 키·프록시로 해외 LLM 호출(Cloud Mode) | **처리자 + 국외이전 주체** | — | 제28조의8 절차 필요, 상대방 동의 불가 → 고위험 |
| S6. B2B: 기업이 자기 상담 데이터로 사용 | 회사는 **수탁자**(제26조) 또는 온프레미스 공급자 | 기업이 처리자 | 기업의 처리 근거와 위탁계약 |

#### (2) 회사가 처리자일 때 상대방 정보의 처리 근거 (제15조 제1항 각 호)
| 근거 | 상대방(B)에 적용 가능성 | 비고 |
|---|---|---|
| 1호 동의 | B가 직접 동의하면 **가장 확실** | 실무상 받기 어려움. 그래서 동의 수집 UX를 따로 설계함(9장) |
| 2호 법률 특별규정 | 없음 | — |
| 4호 계약 이행 | **적용 불가** | 회사와 B 사이에 계약이 없음 **[가능성 높음]** |
| 5호 생명·신체 급박 | 해당 없음 | — |
| 6호 정당한 이익 | **좁게 가능성은 있음** | "명백하게 정보주체의 권리보다 우선", 상당한 관련성, 합리적 범위 요건. 사적 대화를 상업 Persona에 쓰는 이익이 B의 사생활보다 "명백히" 우선한다고 보기는 어려움 **[법률 검토 필요, 부정적]** |
| 제15조 제3항 추가적 이용 | 당초 수집 목적과 합리적 관련성이 필요 | 회사가 B 정보를 '수집'한 근거가 먼저 있어야 함 |
| 제23조 민감정보 | **동의 또는 법령만** | 정당한 이익 적용 불가 **[확실]**. 위반 시 형사처벌 조항(제71조) 있음 |
| 가명정보(제28조의2) | 통계·과학적 연구·공익적 기록보존 | 특정인 Persona는 목적과 충돌. 집계 분석(H, E)에는 여지 있음 **[법률 검토 필요]** |
| AI 특례(제28조의12~15) | 2027-03-09 시행. PIPC 사전 심의·의결, 공익·사회적 이익 목적 | 개인 Persona 상용 서비스는 해당 가능성 낮음 **[가능성 높음]** [S2] |

- 추가로 정보주체 이외로부터 수집한 개인정보(제20조): 회사가 A에게서 B의 정보를 받으면 B가 요구할 때 **수집 출처·목적·처리정지 요구권**을 알려야 합니다. 일정 규모(시행령 기준) 이상이면 먼저 통지해야 합니다 [S1].

#### (3) 동의가 "항상" 필요한가
- **로컬 처리(S1)**: 회사 관점에서 법적으로 동의가 필요하지 않을 가능성이 높습니다. 그래도 제품 정책으로는 다음을 권고합니다.
  - (a) 상대방 Persona 생성은 상대방 동의가 있을 때만
  - (b) 상대방 발화는 Self Persona의 맥락으로만 사용
- **서버 처리(S3/S5)**: 상대방 정보에는 동의 외에 실효적인 근거가 거의 없습니다. 특히 민감정보는 동의가 필수입니다.

#### (4) 가장 안전한 동의 수준(상용 서비스 설계 기준)
| 등급 | 구조 | 권고 |
|---|---|---|
| L0 | 업로더 약관 동의만 | ❌ 이루다 선례상 불충분 |
| L1 | 업로더의 기능별 개별 동의 + "본인이 참여한 대화" 서약 | 로컬 Self/Analytics 최소 요건 |
| L2 | L1 + 상대방은 맥락만, 마스킹, 서버 전송 금지 | **MVP 기본값** |
| L3 | Persona 대상자 본인의 직접 동의(본인 확인, 범위·기간·철회) | 상대방·Creator·직원 Persona의 필수 요건 |
| L4 | L3 + 그룹 내 다른 참여자 정보는 대상자 발화만 남기고 제거 | 단톡·B2B 권고 |
| L5 | 생전 Digital Legacy Consent + 수령인 지정 + 유족 이의 절차 | 고인 Persona의 유일한 권고 구조 |

### 3.3 개인정보 4분류: 익명 / 가명 / 개인 / 민감
| 구분 | 정의 | 법 적용 | 이 서비스에서의 예 |

| **익명정보** | 시간·비용·기술 등을 합리적으로 고려해도 다른 정보로 더 이상 개인을 알아볼 수 없는 정보(제58조의2) | 법 적용 제외 | 다수 이용자의 집계 통계("평균 문장 길이 11.2자") 정도. **특정인 Persona는 정의상 익명이 될 수 없음** |
| **민감정보** | 사상·신념, 노조·정당, 정치적 견해, 건강, 성생활, 유전정보, 범죄경력, 생체인식, 인종·민족(제23조, 시행령 제18조) | 별도 동의 또는 법령 근거, 안전성 확보 | 건강·정신건강·정치·종교·성생활. **가족 문제와 금융정보는 법정 민감정보가 아님**(다만 금융정보는 고위험으로 취급, 계좌번호 등은 마스킹) |

- PIPC는 2026-03-31 「가명정보 처리 가이드라인」을 **위험도 기반**으로 전면 개정했고, **비정형데이터(텍스트) 가명처리 기준**과 표본 검수를 허용했습니다 [S5]. 대화 텍스트 가명처리 기준은 이 문서를 따라야 합니다.

### 3.5 국외이전 (해외 AI API)
- 회사가 개인정보를 국외(OpenAI·Anthropic·Google 서버)로 **제공·처리위탁·보관**하면 국외이전에 해당합니다(제28조의8 제1항). 근거는 다음과 같습니다.
  1. 정보주체의 **별도 동의**(이전 항목, 국가, 시기·방법, 받는 자, 목적·보유기간, 거부 방법·효과 고지)
  2. 법률·조약
  3. 계약 체결·이행을 위해 필요한 처리위탁·보관으로서 처리방침 공개 등
  4. 이전받는 자의 인증
  5. 이전 국가의 적정성 인정 [S1]
- **문제**: 업로더 A에 대해서는 1호나 3호가 가능하지만, **상대방 B에 대해서는 어느 근거도 실효적이지 않습니다.** **[가능성 높음]**
- **권고 설계**:
  - 회사 프록시나 회사 키를 쓰는 Cloud Mode는 **MVP에서 제외**합니다.
  - Cloud를 허용한다면 **BYOK**(사용자가 자기 계정 키를 입력하고 PC에서 직접 호출)로 하고, **사용자 본인 발화와 마스킹된 최소 맥락만** 보냅니다. 상대방 원문은 보내지 않습니다.
  - API 제공자의 데이터 보존·학습 미사용 조건을 사용자에게 고지합니다.
  - BYOK에서 회사가 국외이전 주체가 아닌지는 **[법률 검토 필요]**입니다. PIPC 「생성형 AI 개발·활용 개인정보 처리 안내서」(2025.8)는 API 이용형 LLM 활용을 별도 유형으로 다루므로 함께 검토합니다 [S4].

### 3.6 민감정보
- 카톡 대화 속 건강·정신건강·정치·종교·성생활은 **법정 민감정보**입니다. 가족 문제·금융정보는 법정 민감정보는 아니지만 **고위험 정보**로 같이 취급합니다.
- 회사가 처리하면 **정보주체별 별도 동의**가 필요하고, 위반 시 형사처벌 대상이 될 수 있습니다(제23조, 제71조). 정당한 이익이나 계약 이행으로는 처리할 수 없습니다. **[확실]**
- 이루다 손해배상 1심도 **민감정보 관련 원고에게 더 높은 위자료**(30만 원)를 인정했습니다 [S7].
- 설계:
  - 민감 카테고리 메시지는 Persona 학습(LoRA)에서 **무조건 제외**합니다.
  - Memory 검색에서는 기본 제외하고, 사용자가 개별 메시지 단위로 포함시킬 수 있게 합니다(로컬에 한함).
  - 서버·클라우드 전송은 금지합니다.

### 3.7 통신비밀보호법·정보통신망법 (참여자 vs 제3자)
**조문 구조**
- 통신비밀보호법은 누구든지 전기통신의 **감청**이나 **공개되지 아니한 타인간의 대화**의 녹음·청취를 하지 못하게 하고(제3조 제1항), 위반이나 지득 내용의 공개·누설을 처벌합니다(제16조).
- '감청'은 당사자 동의 없이 전자적 방법으로 통신 내용을 지득·채록하는 것입니다(제2조 제7호) [S10].

**판례**
- **대법원 2016. 10. 13. 선고 2016도8137**: 카카오가 서버에 이미 수신이 완료되어 저장된 대화를 3~7일마다 추출해 제공한 것은 허가된 '실시간 감청' 방식이 아니어서 위법하다고 했습니다. 감청은 **송수신 중인 통신**을 대상으로 한다는 취지입니다(대법원 2012. 11. 29. 선고 2012도7455도 같은 취지) [S10].
- **대법원 2006. 10. 12. 선고 2006도4981**: 대화에 참여한 당사자가 녹음한 것은 '타인간의 대화' 녹음이 아니라고 봤습니다(3인 대화 중 1인 녹음 포함) [S10].
- **정보통신망법 제49조**: 정보통신망에 의해 처리·보관·전송되는 타인의 비밀 침해·누설을 금지합니다.
  - 대법원 2015. 1. 15. 선고 2013도15457은 '침해'를 정보통신망 침입 같은 **부정한 수단으로 취득**하는 것으로 봤습니다.
  - **대법원 2018. 12. 27. 선고 2017도15226**은 동료가 로그인된 PC 메신저의 저장된 대화를 몰래 열람·복사·전송한 행위를 **제49조 위반**으로 인정했습니다. 저장된 메시지도 보호 대상이 될 수 있다는 판단입니다 [S11].

**적용**
| 상황 | 통신비밀보호법 | 정보통신망법·형법 | 판단 |
|---|---|---|---|
| 대화 참여자 A가 **자기 단말에서** 이미 받은 대화를 내보내 AI에 입력 | 이미 수신 완료된 통신이고 A는 당사자이므로 **감청 해당 가능성 낮음** | A는 정당한 접근권자이므로 '부정한 수단 취득' 아님 | **[가능성 높음] 위반 아님**. 단, 내용을 제3자에게 공개하는 것은 별도 문제(명예훼손·사생활) |
| 배우자·연인·동료 C가 **A의 폰·PC에서 몰래** 내보내기 | 이미 수신된 통신이라 '감청'은 아닐 수 있음 | **2017도15226 유형. 제49조 비밀침해, 제48조 접근권한 침해, 형법 제316조 제2항 위험** | **[가능성 높음] 형사 위험** |
| 유족이 **고인의 폰 잠금을 풀고** 내보내기 | 위와 같음 | 사망자의 비밀이 제49조 '타인의 비밀'에 포함되는지, 상속인의 접근권한이 인정되는지 | **[법률 검토 필요]**. 카카오는 고인 데이터를 유족에게 제공하지 않는 정책임 [S14] |
| 회사가 A의 파일을 받아 처리 | 감청 아님 | A가 적법하게 가진 정보를 받는 것이라 2013도15457 기준상 '누설' 해당 가능성 낮음. 다만 PIPA는 별개 | PIPA 문제로 귀결 |

→ **제품 요구사항**
- 가져오기 시 "나는 이 대화의 참여자이며 내 기기에서 내보냈다" 서약을 받습니다.
- 파일 안에 사용자 본인 이름이 있는지 확인합니다(본인 화자 선택 필수).
- **고인 단말에서 추출한 파일은 받지 않는다**는 정책을 둡니다.

### 3.8 저작권
- 저작물은 "인간의 사상 또는 감정을 표현한 창작물"입니다(저작권법 제2조 제1호). "ㅇㅇ", "밥 먹었어?" 같은 짧은 일상 메시지는 **창작성이 인정될 가능성이 낮습니다.** 긴 편지, 시, 독창적인 글은 **저작물이 될 수 있습니다.** **[가능성 높음]**
- 상대방 메시지를 학습(복제)하는 행위:
  - 개인이 가정 내 사적 이용을 하면 사적이용 복제(제30조)가 적용될 여지가 있습니다.
  - 회사가 상업적으로 학습하면 공정이용(제35조의5) 판단 대상입니다.
  - 문체부·한국저작권위원회는 2026-02-26 「생성형 AI 저작물 학습 공정이용 안내서」를 냈고, TDM 면책 입법은 **추진 중이며 아직 시행되지 않았습니다** [S15]. **[가능성 높음]**
- 대량 대화 데이터의 편집물·데이터베이스 보호(제93조 데이터베이스제작자)는 개인 대화 묶음에는 적용 가능성이 낮습니다.
- **실무 위험은 저작권보다 개인정보·인격권이 훨씬 큽니다.** 제품에서는 원문 대량 출력·공유·출판 기능을 빼면 충분합니다.

### 3.10 사망자 Persona
**기본 법리**
- PIPA는 **살아 있는 개인**의 정보만 보호합니다(제2조 제1호) → 고인 자신의 정보는 PIPA 대상이 아닙니다. **[확실]**
- 그러나 다음이 남습니다.
  - ① 대화 속 **생존 상대방(대부분 유족 본인 포함)의 정보** → PIPA
  - ② 사자 명예훼손(형법 제308조, 허위사실)
  - ③ 사자의 인격 왜곡이 유족 고유의 인격권(추모 감정) 침해가 될 가능성
  - ④ 데이터 취득 경로(3.7: 고인 단말 접근)
  - ⑤ 유족 간 분쟁

| 구조 | 법적 방어력 | 이유 |
|---|---|---|
| (a) 생전 동의 없음, 유족 1인이 업로드 | **매우 낮음** | 다른 유족이 반대할 수 있고, 고인 의사 확인이 불가하며, 상대방 정보에 근거가 없음 |
| (b) 유족 동의만(전원 또는 대표) | 낮음~중 | 유족 간 분쟁은 줄지만 고인 의사는 여전히 확인 불가. 상속인의 '동의 권한' 자체가 불명확 **[법률 검토 필요]** |
| (c) 생전 Digital Legacy Consent | **가장 높음** | 본인의 자기결정. 범위·수령인·기간 지정 가능 |
| (d) 여러 대화 상대방 정보 포함 | (c)에도 별도 문제 | 고인의 동의는 **상대방 정보에는 미치지 않음** → 상대방 발화 최소화·마스킹, 수령인 본인이 참여한 대화만 사용 |

→ **최고 방어 구조**
- 생전 Legacy Consent(본인 인증, 공증 수준 기록)
- 수령인이 **자기가 고인과 나눈 대화**만, **자기 단말에서** 내보내 사용
- 고인 발화만 Style/Memory 대상으로 하고 제3자 발화는 마스킹
- 유족 이의 시 Freeze
- 기간 만료 시 자동 은퇴(Retire)

## 4. 가장 안전한 사업 구조 (Local First × Consent First)

### 4.1 원칙
1. **회사는 대화 원문, 가공 데이터, 벡터, 프롬프트를 절대 받지 않습니다.** 서버는 계정, 라이선스, 결제, 동의 레코드(해시), 업데이트 배포만 맡습니다.
2. **Persona 대상은 동의한 사람만 됩니다.** 본인(Self), 동의한 상대방(L3), 생전 동의한 고인(L5), 동의한 직원 집계(E).
3. **상대방 데이터는 "맥락"이지 "모델"이 아닙니다.** 상대방 발화는 스타일 분석, 파인튜닝, Persona 출력 인용에 쓰지 않습니다.
4. **사실은 근거가 있을 때만 말합니다.** 근거 없는 과거 사실은 생성 단계에서 차단합니다(7장).
5. **기본값은 가장 보수적으로 둡니다.** 텔레메트리 OFF, Cloud OFF, 민감정보 제외, 단톡방 Persona 생성 OFF.

| 9 Annotate | 감정, 대화행위, 레지스터, 엔티티 | `MessageAnnotation` | 로컬 LLM 배치 또는 경량 분류기 |

### 6.1 KakaoTalk Parser 설계

**형식 다양성**: 카카오 공식 안내상 PC(Windows)와 Mac은 txt로 저장되고, 모바일은 '텍스트만' 또는 '모든 메시지(미디어 포함)'를 고를 수 있습니다 [S13]. 실제 줄 형식은 OS, 앱 버전, 언어(한국어/영어/일본어 UI), 12/24시간제에 따라 다릅니다. 아래 정규식은 **관측된 예시를 바탕으로 한 출발점**이고, **실제 샘플 코퍼스(버전별 최소 3종 × OS 4종 × 언어 2종)로 검증해야** 합니다.

| 형식(관측 예시) | 날짜 처리 | 메시지 행 패턴 예 |
|---|---|---|
| Windows PC | 구분선 `--------------- 2026년 10월 1일 수요일 ---------------` | `[홍길동] [오후 3:15] 내용` |
| Android | 행마다 날짜 포함 | `2026년 10월 1일 오후 3:15, 홍길동 : 내용` |
| iOS | 행마다 날짜 포함 | `2026. 10. 1. 오후 3:15, 홍길동 : 내용` |
| 영어 UI | 월 이름, AM/PM | `October 1, 2026, 3:15 PM, Name : text` / `[Name] [3:15 PM] text` |
| 구버전 Mac CSV(비공식 관측) | `Date,User,Message` | CSV 파서 |

**왜 Regex 하나가 아니라 Adapter인가**
- 형식마다 날짜가 들어 있는 위치(헤더 vs 행), 화자 구분자, 시간 표기가 다릅니다. 정규식 하나로 합치면 **오탐(내용 속 "2026. 10. 1. 오후 3:15, 누구 : "를 새 메시지로 오인)**이 생기고 유지보수가 어려워집니다.
- **Adapter 패턴 + 점수 기반 탐지 + 골든 파일 테스트**가 맞습니다. 카카오가 형식을 바꾸면 Adapter 하나만 추가하고, 업데이트로 배포해 유지보수 구독의 가치로 만듭니다.

**케이스별 처리 규칙**
| 케이스 | 처리 |
|---|---|
| 날짜 구분 | 헤더형은 `currentDate` 상태 유지, 행 포함형은 행에서 추출. 자정 넘김 대화가 끊기지 않게 세션은 날짜와 무관하게 분할(6.2) |
| 시간 | 오전/오후/AM/PM/24h 모두 지원. 타임존은 내보낸 기기 기준(정보 없음) → 로컬 타임존으로 가정한다고 표시 |
| 여러 줄 메시지 | 메시지 패턴에 맞지 않는 줄은 **직전 메시지에 이어 붙임**. 단, 내용 속 날짜처럼 보이는 줄에 대비해 "화자가 알려진 참여자 목록에 있는지" 2차 검증 |
| 사진/동영상/파일 | `사진`, `사진 N장`, `동영상`, `파일: 이름.ext` 등을 `MessageKind.Media`로 분류. 내용 분석에서는 제외하고 빈도 통계에만 사용 |
| 이모티콘 | `이모티콘` 텍스트(카카오 이모티콘) → `Emoticon`. 유니코드 이모지는 별도 카운트 |
| 시스템 메시지 | 입장/퇴장/초대/내보냄/방장 변경/"메시지가 삭제되었습니다"/"채팅방 관리자가 메시지를 가렸습니다"/보이스톡·페이스톡/송금·정산 → `System` 하위 유형. **사전 + 정규식 사전 파일(JSON)**로 외부화해서 업데이트 가능하게 함 |
| 삭제 메시지 | `Deleted` 플래그. 내용 없음. 대화 흐름(턴 구조)에는 포함 |
| 단톡방 | 참여자 3명 이상이면 `IsGroup`. **MVP는 단톡 Persona 생성 비활성**, 분석만 허용 |
| 동일 이름 | 내보내기 파일에는 사용자 ID가 없으므로 **동명이인은 구분할 수 없음**. 입장/퇴장 이력과 대화 패턴으로 의심 플래그만 띄우고 사용자가 분리·병합. 닉네임 변경은 사용자가 병합 |
| 화자명에 ` : ` 포함 | 참여자 사전이 확정된 뒤 **2-pass 파싱**: 1차로 후보를 추출하고 2차에서 알려진 이름 최장 일치로 재분할 |
| 인코딩 | BOM 검사 → UTF-8 엄격 디코드 실패 시 CP949 시도 |
| 대용량(100만 줄) | 스트리밍 파싱(`IAsyncEnumerable`), 배치 Insert |

### 6.2 Sessionization (Hybrid)
**목표**: 의미 있는 "대화 에피소드" 단위로 나눕니다. 검색 단위, 기억 단위, 감정 상황 단위가 됩니다.

**알고리즘**
```
입력: 같은 채팅방 메시지(시간순), 쌍(pair)별 응답 간격 분포
1) Hard split:  gap ≥ H (기본 6h)                        → 새 세션
2) Hard merge:  gap ≤ S (기본 10m)                       → 같은 세션
3) Adaptive:    S < gap < H 인 경우
     T_pair = clamp(P90(같은 방의 '세션 내' 간격), 20m, 2h)   ← 방·관계마다 다르게 학습
     gap > T_pair 이면 후보 split, 아래 점수로 최종 결정
     score = w1·norm(gap/T_pair)
           + w2·(1 - cos(emb(last k msgs), emb(next k msgs)))   ← 의미 전환
           - w3·continuation_cue(next msg)                      ← "아까", "그래서", "ㅇㅇ", "ㅋㅋㅋ", 답변형
           - w4·unanswered_question(prev window)                ← 직전에 질문이 있었고 답이 없었으면 이어짐
           + w5·greeting_cue(next msg)                          ← "자니?", "굿모닝", "오늘" 등 새 화제 신호
     score ≥ θ 이면 split
4) Long session cap: 토큰이 L(예: 1,500) 초과 시 TextTiling식 유사도 골짜기에서 하위 분할(sub-session)
5) 날짜 변경은 split 기준으로 쓰지 않음(새벽 대화 보존)
```
- 초기 파라미터: k=3, w=(1.0, 1.2, 0.8, 0.6, 0.5), θ=1.0. **수작업 라벨 200개 세션으로 튜닝**합니다. 평가 지표는 WindowDiff/Pk(텍스트 분할 표준 지표)입니다.
- 임베딩 호출 비용을 줄이기 위해 의미 점수는 **후보 경계에서만** 계산합니다.

### 6.3 Embedding / Hybrid Search
- **색인 단위**: ① 세션 요약 + 원문(세션 레벨), ② 대상 인물 발화 묶음(턴 레벨: 상대 발화 → 대상 응답 쌍), ③ MemoryItem(사실 단위). 메시지 하나하나를 임베딩하면 "ㅇㅇ", "ㅋㅋ" 때문에 노이즈가 큽니다.
- **하이브리드 점수**:
```
score(d) = α·cos(q, d)                      (Dense, bge-m3/KURE)
         + β·BM25_norm(q, d)                (SQLite FTS5 trigram — 한국어 형태소 분석기 없이 부분일치)
         + γ·recency(d) = exp(-Δdays/τ)     (회상형 질의면 γ를 낮춤, "요즘" 질의면 높임)
         + δ·participant_match(d)           (질의에 언급된 인물, 현재 대화 상대)
         + ε·entity_overlap(d)              (장소·사건 엔티티)
  → 상위 50개 → (선택) 로컬 reranker(bge-reranker-v2-m3 등, 라이선스 확인) → 상위 8개
  → 동의 필터(ConsentManifest)·민감 필터를 마지막에 다시 적용(누수 방지)
```
- 가중치 시작값은 α 0.55, β 0.25, γ 0.05, δ 0.1, ε 0.05입니다. 평가셋(질문 100개, 정답 세션 라벨)으로 Recall@8을 측정해 조정합니다.
- **벡터 저장소**: Persona 하나당 세션이 보통 수천~수만 개입니다. 1만 개 × 1024차원 float32는 약 40MB여서 **C# 메모리 브루트포스(TensorPrimitives SIMD)**로 충분히 빠릅니다(수 ms). 별도 벡터 DB 없이 **암호화 blob 1개**로 저장하면 삭제·암호화가 단순해집니다. 10만 개 이상이면 int8 양자화 또는 sqlite-vec(v0.1.9, 2026-03) 확장을 검토합니다 [S22].

## 7. Persona Engine Architecture

```
                 ┌──────────── Persona Engine ─────────────┐
 Query/Context → │ ① Memory (무엇이 있었나)  — RAG, 출처 필수   │
                 │ ② Style (어떻게 말하나)  — 측정 프로필+예시  │ → Prompt → LLM → ⑤ Grounding
                 │ ③ Emotion/Situation (어떤 상황에 어떻게) │                ↓
                 │ ④ (선택) Style Adapter (LoRA)           │           ⑥ Safety Policy
                 └──────────────────────────────────────────┘                ↓
                                                                   Render(QUOTE/FACT/INFERRED/GENERATED)
```

### 7.1 Memory (RAG 중심)
- `MemoryItem`은 사람·장소·사건·관계·약속·선호를 담는 **사실 단위**입니다. 모든 항목은 **원문 MessageId 목록(provenance)**을 가집니다.
- 추출은 로컬 LLM이 세션 단위로 JSON 추출 → **규칙 검증**(엔티티가 원문에 실제로 나오는지 문자열 대조) 순서로 합니다. 검증에 실패한 항목은 버립니다.
- **쓰기 금지 원칙**: Persona와 나눈 대화 내용은 MemoryItem으로 **승격하지 않습니다**. AI 대화 로그는 별도 테이블에 두고 Persona 기억 검색에서 제외합니다. 이렇게 해야 허위 기억이 순환 강화되지 않습니다.

### 7.2 Style Profile — 제안 구조 평가와 개선
**평가**: `Formality: 0.3, HumorLevel: 0.6, EmpathyLevel: 0.8` 같은 형태는
- ① Humor/Empathy를 신뢰성 있게 측정할 수 없고,
- ② LLM은 "0.6만큼 유머러스하게" 같은 지시를 일관되게 따르지 못하며,
- ③ 사람의 말투는 **상대와 상황에 따라 달라지는데**(엄마에게는 존댓말, 친구에게는 반말) 단일 수치는 이를 지워 버립니다.

**개선**: **측정 가능한 분포(Measured Features) + 관계별 분할 + 실제 발화 예시(Exemplar)** 3층 구조로 바꿉니다.

```jsonc
StyleProfile {
  "subjectParticipantId": "p_02",
  "scope": "relationship:p_01",          // 관계별 프로필 (전체/상대별)
  "stats": {
    "msgLen": { "p50": 9, "p90": 28 },   // 글자 수 분포
    "burst": { "meanMsgsPerTurn": 2.7 }, // 한 턴에 짧은 메시지 연타
    "replyLatencySec": { "p50": 45 },
    "register": { "haeyo": 0.05, "banmal": 0.92, "hapsyo": 0.03 },   // 종결어미 분류
    "laughter": { "ㅋ": 0.41, "ㅎ": 0.07, "avgRun": 4.2 },          // 메시지당 비율, 평균 반복 길이
    "emoji":    { "rate": 0.12, "top": ["😂","🥲"] },
    "emoticonRate": 0.06,
    "punct": { "noFinalPeriod": 0.95, "tilde": 0.18, "ellipsis": 0.07 },
    "questionRate": 0.21,
    "spacingErrorRate": 0.3,
    "profanityRate": 0.01
  },
  "lexicon": {
    "signatureNgrams": ["ㅇㅋㅇㅋ", "레알", "아 진짜?"],          // 상대 대비 TF-IDF/로그오즈 상위
    "abbreviations": { "ㄱㄱ": "가자", "ㅇㅈ": "인정" },
    "openers": ["야", "헐"], "closers": ["ㅂㅂ", "잘자~"]
  },
  "reactionMap": {                       // 상황(감정×대화행위) → 응답 특성
    "sad|disclosure":  { "style": "짧은 공감 + 질문", "exemplarIds": [ "m_1832", "m_9921" ] },
    "excited|share":   { "style": "ㅋ 연타 + 감탄", "exemplarIds": [ "m_221" ] }
  },
  "describedByLLM": "짧게 여러 번 끊어 보내고, 'ㅋㅋㅋㅋ'를 자주 쓰며 마침표를 거의 안 씀..."  // 통계를 자연어로 요약(프롬프트용)
}
```

**스타일을 실현하는 방식(우선순위)**
1. **Exemplar 검색**(가장 효과 큼): 현재 상황과 비슷한 실제 "상대 발화 → 대상 응답" 쌍 3~8개를 few-shot으로 넣습니다.
2. **자연어 스타일 지시**: 통계를 사람이 읽을 수 있는 규칙 5~10줄로 바꿔 넣습니다.
3. **결정적 후처리(Style Post-processor)**: 문장 분할을 버스트로, 마침표 제거, 'ㅋ' 길이를 분포에서 샘플링, 종결어미 레지스터 교정. LLM이 못 맞추는 표면 특징은 코드로 맞추는 편이 싸고 정확합니다.
4. (필요 시) LoRA Style Adapter (7.4).

**평가**: 실제 홀드아웃 응답과 생성 응답의 특징 분포 거리(JS divergence), 그리고 지인 블라인드 테스트("어느 쪽이 진짜?")로 측정합니다.

### 7.3 Emotion Context — 단순 Sentiment보다 나은 방법
- 수정 사항: `Formal`은 감정이 아니라 레지스터이고, `Affectionate`는 감정이라기보다 **관계적 태도**에 가깝습니다. 다음 **4개 축**으로 나눕니다.

| 축 | 라벨 예 | 방법 |
|---|---|---|
| 감정(Emotion) | 기쁨, 설렘, 슬픔, 분노, 불안, 서운함, 미안함, 고마움, 피곤, 중립 (+ valence/arousal 연속값) | 로컬 LLM zero-shot(JSON 출력) → 사용자 수정 샘플로 경량 분류기 증류(선택). 한국어 감정 데이터셋(KOTE 등)은 **라이선스 확인 후** 사용 |
| 대화행위(Dialogue Act) | 질문, 답변, 요청, 제안, 공유, 자기노출, 위로, 농담, 놀림, 사과, 감사, 갈등, 인사 | 같은 LLM 호출로 함께 라벨링 |
| 레지스터 | 합쇼체/해요체/반말/혼합 | **규칙 기반**(종결어미 분석) — LLM 불필요 |
| 대상·강도 | 감정 대상(상대/제3자/상황), 강도 1~3 | LLM |

- **단위**: 메시지 단독 라벨은 부정확합니다("ㅋㅋ"는 맥락 의존적). **이전 k개 메시지를 맥락으로 넣고 턴 단위**로 라벨링합니다.
- **Situation → Response 학습**: (상대의 감정·행위) → (대상의 응답 행위·레지스터·길이) 전이 통계와 Exemplar 인덱스를 만듭니다. 이것이 `reactionMap`입니다. 채팅할 때 현재 사용자 메시지를 같은 축으로 라벨링하고 → 같은 상황의 Exemplar를 검색합니다.
- 감정 라벨은 **추정치**입니다. UI에서 "AI가 추정한 감정"으로 표시합니다. 고인의 감정 상태를 단정하는 표현("그때 너무 슬퍼했어")은 Grounding 정책에 따라 INFERRED로 처리합니다.

### 7.4 Fine-tuning이 필요한가
| 상황 | RAG + 시스템 프롬프트 + Exemplar로 충분 | LoRA가 필요할 수 있음 |
|---|---|---|
| 모델 크기 | 8B 이상 instruct 모델 | 1~4B 소형 모델(8GB PC)에서 지시 준수력이 부족할 때 |
| 스타일 특성 | 레지스터, 웃음, 이모지, 길이 → 프롬프트+후처리로 대부분 달성 | 독특한 어휘 조합, 리듬, 말장난 습관이 프롬프트로 재현되지 않을 때 |
| 데이터량 | 대상 발화 수백 개면 Exemplar 방식이 유리 | 대상 발화 수천 개 이상 + 품질 평가에서 유의미한 차이가 있을 때 |
| 지연·토큰 | 컨텍스트가 길어짐 | 프롬프트 길이를 줄여 속도 개선 |

**파인튜닝에 과거 사실을 넣으면 생기는 문제**
1. **출처를 제시할 수 없음**: 응답이 어떤 메시지에 근거했는지 알 수 없습니다.
2. **혼합 기억(confabulation)**: 서로 다른 사건이 섞여 그럴듯한 허위 기억이 생깁니다. 제주도 예시가 바로 이 현상입니다.
3. **개별 삭제·정정 불가**: 특정 메시지 삭제 요청이 들어와도 어댑터 전체를 다시 학습해야 합니다(10.6 Unlearning).
4. **추출 공격**: 학습 데이터가 프롬프트로 추출될 수 있습니다 [S27].
5. **동의 범위 관리 불가**: 상대방 발화가 섞이면 분리할 수 없습니다.

→ **결론**: MVP1~2에서는 파인튜닝을 하지 않습니다. MVP3에서 실험적으로 넣을 경우 **(a) 대상 본인 발화만, (b) 민감·PII 제거, (c) 사실 서술형 문장 필터링(스타일 쌍만), (d) 대상 본인의 "Fine-tuning Allowed" 동의, (e) 로컬 학습만, (f) 어댑터를 데이터셋 Vault 안에 두고 키 파기로 삭제**합니다.

### 7.5 Hallucination / False Memory 방지
**위협 모델**: 고인이나 상대방이 **하지 않은 말**, **없었던 사건**("우리 그때 제주도 갔었잖아")을 사실처럼 말하는 것.

**구조: 생성 전 계획 → 제약 생성 → 생성 후 검증**
```
1. Retrieve: 하이브리드 검색 → Evidence[] (MessageId, 원문, 시간, 점수)
2. Plan:     LLM에 "응답 계획"만 JSON으로 요청
             { segments: [ {type:"QUOTE", evidence:["m_812"]}, {type:"CLAIM", text:"...", evidence:["m_812","m_815"]},
                           {type:"STYLE_ONLY", intent:"공감+질문"} ] }
3. Generate: 계획에 묶인 생성. 과거 사건 서술은 evidence가 있는 CLAIM 슬롯에서만 허용
4. Verify (생성기와 분리):
   a) QUOTE: 원문과 정확히 일치하는지 해시/문자열 대조 → 불일치면 QUOTE 지위 박탈
   b) Past-event claim 추출: 규칙(과거시제+장소/시간/인물 엔티티, "~했잖아", "~갔었지") + LLM 추출
   c) 각 claim이 evidence에 의해 함의되는지 검사(NLI 또는 LLM judge, 로컬)
   d) 근거 없는 과거 사실 → 삭제하거나 "기록에서는 못 찾았어. 언제였지?" 같은 질문형으로 재작성
5. Label & Render
```

**내부 상태 라벨(평가: 유효합니다. 다만 라벨은 생성기가 아니라 검증기가 붙여야 합니다)**
| 라벨 | 정의 | 판정 방법 | UI |
|---|---|---|---|
| **QUOTE** | 과거 실제 메시지를 그대로 인용 | 원문 해시 일치 | 인용 카드(날짜·원문), "실제 기록" 배지 |
| **FACT** | 근거 메시지로 뒷받침되는 과거 사실의 재서술 | NLI 함의 ≥ τ, 근거 2개 이상 또는 1개 + 고신뢰 | 밑줄, 클릭 시 근거 표시 |
| **INFERRED** | 패턴에서 추론한 성향·선호("너 매운 거 좋아했잖아") | 다수 메시지 통계 근거 | "기록에서 추정" 아이콘 |
| **GENERATED** | 새로 생성한 말(인사, 공감, 질문). 과거 사실 주장 없음 | 사실 주장 없음 확인 | 기본 AI 버블 |
| (차단) UNSUPPORTED | 근거 없는 과거 사실 | 검증 실패 | 표시하지 않음, 감사 로그 |

- **Confidence Score** = f(검색 점수, 함의 확률, 근거 개수, 근거 시점 일관성). 임계값 아래면 FACT → INFERRED로 강등하거나 질문형으로 바꿉니다.
- **"왜 이렇게 답했나요?"**: 응답마다 사용한 Evidence 목록, StyleExemplar 목록, 차단된 claim 수를 보여줍니다.
- **기술적 구분 보장**: QUOTE는 LLM 출력이 아니라 **DB에서 원문을 직접 렌더링**합니다. LLM은 "m_812를 인용"이라는 참조만 출력하므로 원문 위조가 구조적으로 불가능합니다.

## 8. Privacy Engine

### 8.1 제안된 4-Layer 구조 평가
- **평가**: 방향은 맞습니다. 다만 ① 각 레이어의 **목적(무엇을 위해 가리는가)**이 정의되지 않았고, ② 대화 맥락이 필요한 기능(Memory)과 가려야 하는 기능(Cloud, Export, LoRA)이 같은 마스킹을 쓰면 품질이나 보호 중 하나가 무너집니다.
- **개선**: **탐지는 한 번, 마스킹은 용도별 정책(Purpose-based Redaction)**으로 나눕니다.

```
Detect(1회) ──► PiiFinding{span, type, confidence, layer, subjectParticipant?}
                   │
       ┌───────────┼───────────────┬──────────────────┬─────────────────┐
       ▼           ▼               ▼                  ▼                 ▼
  LocalMemory   StyleAnalysis   LoRA Training     Cloud(BYOK)       Export/Share
  (원문 유지,    (식별자 토큰화)  (PII·민감 문장     (최소 맥락,       (기본 금지)
   민감=옵트인)                    전부 제거)         일관 가명)
```

### 8.2 레이어 설계
| Layer | 대상 | 방법 | 비고 |
|---|---|---|---|
| L1 Pattern | 전화번호, 주민등록번호(체크섬 검증), 외국인등록번호, 여권번호, 운전면허번호, 이메일, 카드번호(Luhn), 계좌번호(은행별 자릿수+키워드 근접), IP, URL, 주소(도로명 패턴), 차량번호, 생년월일 | 정규식 + 검증 함수 + 문맥 키워드 | 고유식별정보(제24조) 탐지 시 **무조건 마스킹** |
| L2 NER | 인명, 조직, 학교, 병원, 지역, 직책 | 로컬 한국어 NER(소형 토큰분류 모델 ONNX — 상용 라이선스 확인) + **참여자 이름 사전**(파일에서 이미 앎) + 호칭 사전("민수야", "김대리님") | 한국어 이름은 일반 단어와 겹침("하늘", "보람") → 사전+문맥 결합 |
| L3 Context-Sensitive | 건강·정신건강·정치·종교·성생활·범죄·가족 갈등·금융 상태·위치 동선 | 로컬 LLM 분류(문장+앞뒤 2문장) → `SensitiveCategory`, 주체(누구의 정보인가), 확신도 | "우리 엄마 서울대병원에서 암 치료 중" → 건강(주체: 화자 모친, 제3자), 기관명, 질병 |
| L3.5 Quasi-identifier | 단독으로는 무해하지만 조합하면 식별되는 정보(직장+동네+나이) | 세션 단위 엔티티 조합 위험 점수 | Cloud 전송·Export 전에만 적용 |
| L4 User Review | 고위험 우선 정렬, 일괄 처리 | 삭제 / 마스킹 / 유지(로컬 한정) / "이 사람 관련 전부 제외" | 결정을 감사 로그에 기록 |

### 8.3 추가 권고
- **주체(subject) 귀속**: 민감정보가 "누구의 정보인지"(화자 본인, 상대, 제3자)를 기록합니다. 동의 상태와 결합해야 정책을 적용할 수 있습니다.
- **일관 가명(consistent pseudonym)**: 같은 사람은 같은 토큰(`[PERSON_3]`)으로 바꿉니다. 매핑 테이블은 Vault 안에서 별도 키로 암호화합니다(가명정보의 '추가정보' 분리 보관 취지).
- **품질 측정**: 직접 라벨링한 1,000문장 평가셋으로 레이어별 Recall과 Precision을 측정합니다. 목표 예시는 L1 Recall ≥ 0.99, L3 Recall ≥ 0.85입니다. **"개인정보 완전 제거"라는 표현은 쓰지 않습니다.**
- **오탐 비용**: 과도하게 마스킹하면 Memory 품질이 무너집니다. 로컬 Memory는 원문을 유지하고, 외부로 나가는 경로에서만 강하게 마스킹합니다.

### 9.3 다자간 단톡방 (A가 업로드, B·C·D 미동의)
| 목적 | 처리 |
|---|---|
| A의 Self Persona | A 발화는 Style 대상. B·C·D 발화는 **ContextOnly**(A가 무엇에 반응했는지 알기 위한 직전 1~3턴, 이름 가명화) |
| A의 대화 분석(H) | A 자신 지표는 상세히. 타인 지표는 **집계 수준**(누가 가장 많이 말했나 정도). 타인별 감정 변화 분석은 **기본 OFF**(감시 도구화 방지) |

| B가 나중에 철회 | 동의 레지스트리 철회 → A의 앱이 다음 동기화 때 B 관련 인덱스·Style·Exemplar 삭제, 감사 로그 기록 |

### 9.4 동의 수집 UX(L3)와 Local First의 충돌 해결
- 동의 레지스트리 서버가 필요합니다. 여기에는 **내용 없이** 동의ID, 대상자 본인 확인 결과(해시), 범위, 만료, 철회만 저장합니다. 이 서버는 PIPA상 개인정보 처리(대상자 연락처·인증 결과)이므로 처리방침에 반영해야 합니다.
- 흐름: A가 "김OO에게 동의 요청" → 링크 발송(A가 직접 공유) → B가 웹에서 본인 확인(휴대폰 OTP 또는 본인확인기관) → **범위 선택**(기억/말투/민감 카테고리/기간/누가 대화하나) → 서명 → A 앱이 consentId를 검증.
- 앱은 7일마다 철회 여부를 확인합니다(요청에는 consentId만 포함). 오프라인이 30일을 넘으면 B Persona를 **일시정지**합니다.

## 10. Security Architecture

### 10.1 저장 암호화와 키 관리
| 항목 | 설계 |
|---|---|
| 키 계층 | **KEK**(사용자·기기 바인딩): Windows DPAPI(CurrentUser) 또는 Windows Credential Manager. 선택적으로 사용자 패스프레이즈 + Argon2id로 추가 보호 → **DEK**(데이터셋별 256-bit 랜덤) |
| DB | 데이터셋별 SQLCipher DB(AES-256). 키 = DEK에서 HKDF로 파생. SQLCipher .NET 패키징은 커뮤니티 빌드와 상용(Zetetic) 라이선스가 갈리므로 **배포 라이선스 확인 필요** |
| 벡터·어댑터·원문 | AES-256-GCM(`System.Security.Cryptography.AesGcm`), 파일 단위 nonce, 헤더에 버전/키ID |
| 메모리 | 복호화 버퍼 최소화, 키 사용 후 `CryptographicOperations.ZeroMemory`. .NET GC 특성상 완전 제거는 불가하다는 점을 인지 |
| 데이터 위치 | `%LOCALAPPDATA%\<App>\vault` (**Documents 폴더 금지** — OneDrive 폴더 리디렉션으로 클라우드에 동기화될 수 있음) |

### 10.2 삭제 — Secure Delete의 한계와 Crypto-shredding
- SSD/NVMe는 웨어레벨링과 TRIM 때문에 **덮어쓰기가 같은 물리 셀에 간다는 보장이 없습니다**. 그 밖에 VSS 섀도 복사본, 파일 히스토리, OneDrive 휴지통, pagefile.sys, hiberfil.sys, 크래시 덤프에 사본이 남을 수 있습니다.
- 따라서 **삭제 보장은 키 파기로 정의**합니다. DEK를 파기하면 남은 암호문 조각은 복호화할 수 없습니다. 파일 삭제와 덮어쓰기는 보조 수단입니다.
- 사용자 고지 문구 예: "삭제 시 암호화 키를 파기하여 복구할 수 없게 합니다. 단, 이 앱 밖에서 만든 백업이나 원본 내보내기 파일(.txt)은 직접 삭제해야 합니다."

### 10.3 "모든 데이터 삭제" 범위
| 대상 | 위치 | 삭제 방법 | 확인 |
|---|---|---|---|
| 원문(가져온 사본) | vault/{ds}/raw.enc | DEK 파기 + 파일 삭제 | 존재 검사 |
| 파싱·가공 데이터, FTS 색인 | data.db(SQLCipher) | DEK 파기 + 파일 삭제(-wal, -shm 포함) | 〃 |
| Embedding/Vector | vectors.bin | DEK 파기 + 삭제 | 〃 |
| Memory Items, Style Profile, Exemplar | data.db | 〃 | 〃 |
| 검색 캐시, 임베딩 캐시 | cache/{ds}/ | 파일 삭제(캐시도 DEK로 암호화하도록 설계) | 〃 |
| Prompt history / Chat log | chats.db(데이터셋별) | DEK 파기 | 〃 |
| Fine-tuned Adapter | vault/{ds}/adapter/ | DEK 파기 + 삭제. **어댑터를 앱 밖으로 내보내는 기능 없음** | 〃 |

### 10.4 로그·크래시·텔레메트리
- 로그에는 **메시지 내용, 이름, 파일명, 프롬프트를 절대 기록하지 않습니다**. 구조화 로그에 ID와 카운트만 남기고, 로거 레벨에서 문자열 필드를 화이트리스트로 관리합니다.
- 크래시 리포트: 기본 OFF. 켜더라도 **스택트레이스만** 보내고 미니덤프(메모리 포함)는 금지합니다. 예외 메시지에 사용자 데이터가 섞일 수 있으므로 `Exception.Message`는 해시 처리합니다.
- 텔레메트리: 기본 OFF, 옵트인. 기능 사용 횟수 같은 집계만 보냅니다. 처리방침에 항목을 열거합니다.

### 10.5 Embedding과 모델에 남는 개인정보
- **임베딩**: 역변환 공격으로 원문이 상당 부분 복원된다는 연구가 있습니다 [S26]. → 원문과 같은 등급으로 취급(암호화, 동의 범위 적용, 삭제)합니다.
- **파인튜닝 어댑터**: 학습 데이터 암기와 추출 위험이 있습니다 [S27]. → 어댑터는 해당 데이터셋의 파생 개인정보로 봅니다. 공유와 마켓 판매를 금지합니다.
- **Model Unlearning**: 특정 데이터만 지우는 기법은 연구 단계이고 완전성을 보장하지 못합니다. → 삭제·철회 요청이 오면 **어댑터 전체를 폐기하고, 남은 데이터로 재학습할지 사용자가 선택**하게 합니다. 그래서 어댑터 학습 시간이 짧은 소형 LoRA로 한정합니다.

### 10.6 로컬 위협(랜섬웨어·악성코드·다른 프로세스)
- 로컬 LLM API: Ollama를 쓸 경우 `127.0.0.1` 바인딩을 강제하고 `OLLAMA_HOST`를 검사합니다. 무인증이라 같은 사용자 권한의 악성 프로세스가 호출할 수 있으므로 **상용판은 LLamaSharp 인프로세스 전환**을 권고합니다.
- 실행 중에는 Vault 잠금(자동 잠금 5분, Windows Hello 재인증 옵션)을 둡니다. 복호화된 데이터는 디스크에 임시 파일로 쓰지 않습니다.
- 랜섬웨어: 로컬 E2E 백업과 백업 무결성 검사로 대응합니다. 이미 감염된 PC는 보호할 수 없다는 점을 고지합니다(위협 모델 범위 밖).

```csharp
namespace TalkPro.Ingestion.Kakao.Adapters;

using System.Globalization;
using System.Text.RegularExpressions;

/// Android 한국어: "2026년 10월 1일 오후 3:15, 홍길동 : 내용"  (실제 샘플로 검증 필요)
public sealed partial class AndroidKoAdapter : IChatFormatAdapter
{
    public string Id => "kakao.android.ko.v1";

    [GeneratedRegex(@"^(?<y>\d{4})년 (?<mo>\d{1,2})월 (?<d>\d{1,2})일 (?<ap>오전|오후) (?<h>\d{1,2}):(?<mi>\d{2}), (?<rest>.+)$",
        RegexOptions.CultureInvariant, matchTimeoutMilliseconds: 50)]
    private static partial Regex MessageLine();

    public double Score(IReadOnlyList<string> head)
    {
        int hits = head.Count(l => MessageLine().IsMatch(l));
        return head.Count == 0 ? 0 : (double)hits / head.Count;
    }

    public LineParseResult ParseLine(string line, ParserState state)
    {
        if (string.IsNullOrWhiteSpace(line)) return new(LineType.Empty);
        var m = MessageLine().Match(line);
        if (!m.Success) return new(LineType.Continuation, Text: line);

        int hour = int.Parse(m.Groups["h"].Value, CultureInfo.InvariantCulture) % 12;
        if (m.Groups["ap"].Value == "오후") hour += 12;
        var local = new DateTime(
            int.Parse(m.Groups["y"].Value), int.Parse(m.Groups["mo"].Value), int.Parse(m.Groups["d"].Value),
            hour, int.Parse(m.Groups["mi"].Value), 0, DateTimeKind.Unspecified);
        var ts = new DateTimeOffset(local, state.Zone.GetUtcOffset(local));

        // "홍길동 : 내용" — 이름에 " : "가 있을 수 있으므로 1차는 첫 구분자, 2차 패스에서 참여자 사전으로 재분할
        var rest = m.Groups["rest"].Value;
        int sep = rest.IndexOf(" : ", StringComparison.Ordinal);
        if (sep < 0) return new(LineType.Message, ts, Speaker: null, Text: rest);   // 시스템 메시지 후보
        return new(LineType.Message, ts, rest[..sep], rest[(sep + 3)..]);
    }
}
```

```csharp
namespace TalkPro.Ingestion.Kakao;

public sealed class KakaoParser(IEnumerable<IChatFormatAdapter> adapters, SystemMessageClassifier systemClassifier)
{
    private const double MinScore = 0.35;

    public async Task<ParsedChat> ParseAsync(Stream input, CancellationToken ct)
    {
        using var reader = new StreamReader(input, EncodingDetector.Detect(input), detectEncodingFromByteOrderMarks: true);
        var lines = new List<string>();
        while (await reader.ReadLineAsync(ct) is { } line) lines.Add(line);

        var head = lines.Take(200).ToList();
        var adapter = adapters.MaxBy(a => a.Score(head))
                      ?? throw new UnsupportedFormatException();
        if (adapter.Score(head) < MinScore) throw new UnsupportedFormatException();

        // Pass 1: 행 분류 및 메시지 조립(연속 줄은 직전 메시지에 결합)
        var state = new ParserState();
        var drafts = new List<MessageDraft>();
        var warnings = new List<ParseWarning>();
        for (int i = 0; i < lines.Count; i++)
        {
            var r = adapter.ParseLine(lines[i], state);
            switch (r.Type)
            {
                case LineType.Message:
                    drafts.Add(new MessageDraft(i + 1, r.Timestamp!.Value, r.Speaker, r.Text ?? ""));
                    break;
                case LineType.Continuation when drafts.Count > 0:
                    drafts[^1].AppendLine(r.Text!);
                    break;
                case LineType.Continuation:
                    warnings.Add(new ParseWarning(i + 1, "ORPHAN_LINE"));
                    break;
            }
        }

        // Pass 2: 참여자 사전 확정 → 이름 최장 일치로 화자 재분할 → 시스템/미디어 분류
        var participants = SpeakerResolver.BuildParticipants(drafts);
        var messages = drafts
            .Select(d => systemClassifier.Classify(SpeakerResolver.Resplit(d, participants)))
            .ToList();
        return new ParsedChat(adapter.Id, RoomTitleExtractor.TryGet(head), participants, messages, warnings);
    }
}
```

```csharp
namespace TalkPro.Privacy;

public enum PiiType { Phone, ResidentId, Email, Account, Card, Ip, Url, Address, Person, Org, School, Hospital, Location, Title,
                      Health, MentalHealth, Political, Religion, Sexual, Criminal, FinancialStatus, FamilyConflict }

public sealed record PiiFinding(string MessageId, int Start, int Length, PiiType Type,
                                double Confidence, string Layer, string? SubjectParticipantId);

public interface IPiiDetector
{
    string Layer { get; }
    IAsyncEnumerable<PiiFinding> DetectAsync(IReadOnlyList<ChatMessage> window, CancellationToken ct);
}

public sealed class PrivacyDetector(IEnumerable<IPiiDetector> layers)
{
    /// L1→L2→L3 순차 실행, 겹치는 span은 높은 위험 유형 우선으로 병합
    public async Task<IReadOnlyList<PiiFinding>> ScanAsync(IReadOnlyList<ChatMessage> messages, CancellationToken ct)
    {
        var all = new List<PiiFinding>();
        foreach (var layer in layers)
            await foreach (var f in layer.DetectAsync(messages, ct)) all.Add(f);
        return SpanMerger.Merge(all);
    }
}

public sealed partial class RegexPiiDetector : IPiiDetector
{
    public string Layer => "L1";

    [GeneratedRegex(@"(?<!\d)01[016789][-.\s]?\d{3,4}[-.\s]?\d{4}(?!\d)", RegexOptions.None, 50)]
    private static partial Regex Phone();
    [GeneratedRegex(@"(?<!\d)(\d{6})[-\s]?([1-8]\d{6})(?!\d)", RegexOptions.None, 50)]
    private static partial Regex Rrn();

    public async IAsyncEnumerable<PiiFinding> DetectAsync(IReadOnlyList<ChatMessage> window,
        [System.Runtime.CompilerServices.EnumeratorCancellation] CancellationToken ct)
    {
        foreach (var msg in window)
        {
            ct.ThrowIfCancellationRequested();
            foreach (Match m in Phone().Matches(msg.Text))
                yield return new(msg.Id, m.Index, m.Length, PiiType.Phone, 0.98, Layer, msg.SpeakerId);
            foreach (Match m in Rrn().Matches(msg.Text))
                if (IsValidRrnChecksum(m.Groups[1].Value + m.Groups[2].Value))   // 오탐 감소
                    yield return new(msg.Id, m.Index, m.Length, PiiType.ResidentId, 0.99, Layer, msg.SpeakerId);
        }
        await Task.CompletedTask;
    }

    private static bool IsValidRrnChecksum(string d) { /* 가중치 2..9,2..5 체크섬. 2020-10 이후 발급분은 체크섬 미적용 → 형식만으로도 위험 처리 */ return true; }
}

/// 용도별 마스킹: 같은 Finding이라도 목적에 따라 다르게 처리
public enum RedactionPurpose { LocalMemory, StyleAnalysis, FineTuning, CloudTransfer, Export }

        RedactionPurpose.StyleAnalysis => Apply(msg.Text, findings),                       // 식별자 → 일관 토큰
```

### 11.6 ConversationSessionizer
```csharp
namespace TalkPro.Memory;

public sealed record SessionizerOptions(
    TimeSpan HardMerge, TimeSpan HardSplit, TimeSpan MinAdaptive, TimeSpan MaxAdaptive,
    int Window = 3, double Threshold = 1.0, int MaxTokens = 1500)
{
    public static SessionizerOptions Default => new(TimeSpan.FromMinutes(10), TimeSpan.FromHours(6),
                                                    TimeSpan.FromMinutes(20), TimeSpan.FromHours(2));
}

public sealed class ConversationSessionizer(IEmbeddingClient embedder, IDiscourseCueDetector cues, SessionizerOptions opt)
{
    public async Task<IReadOnlyList<Session>> SplitAsync(IReadOnlyList<ChatMessage> msgs, CancellationToken ct)
    {
        var content = msgs.Where(m => m.Kind != MessageKind.System).ToList();
        var tAdaptive = LearnAdaptiveThreshold(content);
        var boundaries = new List<int> { 0 };

        for (int i = 1; i < content.Count; i++)
        {
            var gap = content[i].Timestamp - content[i - 1].Timestamp;
            if (gap <= opt.HardMerge) continue;
            if (gap >= opt.HardSplit) { boundaries.Add(i); continue; }
            if (gap <= tAdaptive) continue;

            // 후보 경계에서만 의미 점수 계산(비용 절감)
            var before = content.Skip(Math.Max(0, i - opt.Window)).Take(Math.Min(opt.Window, i));
            var after = content.Skip(i).Take(opt.Window);
            double semShift = 1 - await embedder.CosineAsync(Join(before), Join(after), ct);

            double score = 1.0 * Math.Min(gap / tAdaptive, 3.0) / 3.0 * 2
                         + 1.2 * semShift
                         - 0.8 * cues.ContinuationScore(content[i].Text)      // "아까", "그래서", "ㅇㅇ"
                         - 0.6 * (cues.EndsWithUnansweredQuestion(content, i) ? 1 : 0)
                         + 0.5 * cues.GreetingScore(content[i].Text);         // "자니?", "굿모닝"
            if (score >= opt.Threshold) boundaries.Add(i);
        }
        return BuildSessions(content, boundaries).SelectMany(s => SplitLong(s, opt.MaxTokens)).ToList();
    }

    /// 같은 방의 '짧은 간격' 분포의 P90을 [Min, Max]로 clamp → 관계마다 다른 임계값
    private TimeSpan LearnAdaptiveThreshold(IReadOnlyList<ChatMessage> m)
    {
        var gaps = m.Zip(m.Skip(1), (a, b) => b.Timestamp - a.Timestamp)
                    .Where(g => g < opt.HardSplit).OrderBy(g => g).ToList();
        if (gaps.Count < 20) return TimeSpan.FromMinutes(30);
        var p90 = gaps[(int)(gaps.Count * 0.9)];
        return p90 < opt.MinAdaptive ? opt.MinAdaptive : p90 > opt.MaxAdaptive ? opt.MaxAdaptive : p90;
    }
    // Join, BuildSessions, SplitLong(TextTiling 유사도 골짜기) 생략
}
```

```csharp
public sealed class EmbeddingService(IEmbeddingClient client, int batchSize = 32)
{
    public async Task<float[][]> EmbedAsync(IReadOnlyList<string> texts, CancellationToken ct)
    {
        var result = new List<float[]>(texts.Count);
        foreach (var batch in texts.Chunk(batchSize))
            result.AddRange(await client.EmbedAsync(batch, ct));               // 정규화(L2)된 벡터 반환 가정
        return result.ToArray();
    }

/// 데이터셋 단위 메모리 브루트포스 검색. 디스크에는 AES-GCM 암호화 blob으로만 저장.
public sealed class VectorMemoryStore(IVaultCrypto crypto, string datasetId)
{
    private float[] _matrix = [];          // N × D 연속 배열
    private string[] _ids = [];
    private int _dim;

    public IReadOnlyList<(string Id, float Score)> Search(ReadOnlySpan<float> query, int k, Func<string, bool> allowed)
    {
        var scores = new List<(string, float)>(_ids.Length);
        for (int i = 0; i < _ids.Length; i++)
        {
            if (!allowed(_ids[i])) continue;                                    // 동의·민감 필터를 검색 단계에서도 적용
            var row = new ReadOnlySpan<float>(_matrix, i * _dim, _dim);
            scores.Add((_ids[i], TensorPrimitives.Dot(query, row)));           // 정규화 벡터 → 내적 = 코사인
        }
        return scores.OrderByDescending(s => s.Item2).Take(k).ToList();
    }

    public async Task SaveAsync(string path, CancellationToken ct)
        => await crypto.EncryptToFileAsync(datasetId, VectorCodec.Serialize(_ids, _matrix, _dim), path, ct);

    public void RemoveWhere(Func<string, bool> predicate) { /* 철회된 참여자 벡터 제거 후 재저장 */ }
}

public sealed class HybridRetriever(VectorMemoryStore vectors, FtsIndex fts, ConsentPolicyEngine policy, RetrievalWeights w)
{
    public async Task<IReadOnlyList<Evidence>> RetrieveAsync(RetrievalQuery q, CancellationToken ct)
    {
        var dense = vectors.Search(q.Embedding, 50, id => policy.CanRetrieve(q.DatasetId, id));
        var sparse = await fts.SearchTrigramAsync(q.Text, 50, ct);
        var fused = ScoreFusion.Combine(dense, sparse, q, w);                     // α·cos + β·bm25 + γ·recency + δ·participant + ε·entity
        return policy.FilterEvidence(q.DatasetId, fused.Take(8));                // 마지막 단계 재필터(누수 방지)
    }
```

```csharp
public sealed class GroundingVerifier(IClaimExtractor claims, IEntailmentJudge judge, IMessageRepository repo)
{
    public async Task<GroundedResponse> VerifyAsync(ResponsePlan plan, IReadOnlyList<Evidence> evidence, CancellationToken ct)
    {
        var output = new List<ResponseSegment>();
        int blocked = 0;
        foreach (var seg in plan.Segments)
        {
            if (seg.QuoteId is { } qid)                                          // QUOTE: DB 원문을 직접 렌더
            {
                var original = await repo.GetTextAsync(qid, ct);
                if (original is not null && evidence.Any(e => e.MessageId == qid))
                    output.Add(new(SegmentLabel.Quote, original, [qid], 1.0));
                else blocked++;
                continue;
            }
            var pastClaims = claims.ExtractPastEventClaims(seg.Text);           // "~했잖아", 장소/시간/인물 + 과거시제
            if (pastClaims.Count == 0) { output.Add(new(SegmentLabel.Generated, seg.Text, [], 1.0)); continue; }

            var support = await judge.ScoreAsync(pastClaims, evidence, ct);      // 로컬 NLI/LLM judge
            if (support.Min >= 0.8 && support.EvidenceIds.Count >= 1)
                output.Add(new(SegmentLabel.Fact, seg.Text, support.EvidenceIds, support.Min));
            else if (support.IsPatternInference)
                output.Add(new(SegmentLabel.Inferred, seg.Text, support.EvidenceIds, support.Min));
            else
            {
                blocked++;
                output.Add(new(SegmentLabel.Generated, Rephrase.AsQuestion(pastClaims[0]), [], 0)); // "기록엔 없는데, 언제였지?"
            }
        }
        return new GroundedResponse(output, blocked, plan.ExemplarIds);
    }
}
```

```csharp
namespace TalkPro.Security;

using System.Security.Cryptography;

public sealed class KeyManager(string keyDir)
{
    // KEK = DPAPI(CurrentUser)로 보호. DEK는 데이터셋마다 랜덤 생성, KEK로 래핑해 저장
    public byte[] GetOrCreateDek(string datasetId)
    {
        var path = Path.Combine(keyDir, $"{datasetId}.dek");
        if (File.Exists(path))
            return ProtectedData.Unprotect(File.ReadAllBytes(path), Entropy(datasetId), DataProtectionScope.CurrentUser);
        var dek = RandomNumberGenerator.GetBytes(32);
        File.WriteAllBytes(path, ProtectedData.Protect(dek, Entropy(datasetId), DataProtectionScope.CurrentUser));
        return dek;
    }

    /// Crypto-shredding: 래핑된 DEK 파일을 무작위로 덮어쓴 뒤 삭제. 삭제 보장의 핵심은 '키가 더 이상 없다'는 것
    public void DestroyDek(string datasetId)
    {
        var path = Path.Combine(keyDir, $"{datasetId}.dek");
        if (!File.Exists(path)) return;
        var len = (int)new FileInfo(path).Length;
        File.WriteAllBytes(path, RandomNumberGenerator.GetBytes(len));
        File.Delete(path);
    }

    private static byte[] Entropy(string datasetId) => SHA256.HashData(System.Text.Encoding.UTF8.GetBytes("talkpro:" + datasetId));
}

public sealed class DataDeletionService(KeyManager keys, ILlmClient llm, IVaultPaths paths, IBackupClient backup,
                                        IAuditLog audit, IConsentRegistryClient registry)
{
    public async Task<DeletionReport> DeleteDatasetAsync(string datasetId, CancellationToken ct)
    {
        var report = new DeletionReport(datasetId);
        await llm.UnloadAsync(ct);                                                 // 1. 런타임 캐시 해제
        keys.DestroyDek(datasetId);                                                // 2. 키 파기(이 시점부터 복호화 불가)
        report.KeyDestroyed = true;

        foreach (var p in paths.AllArtifacts(datasetId))                           // 3. raw, db(-wal,-shm), vectors, adapter, chats, cache
            report.Add(p, BestEffortDelete(p));

        report.BackupInvalidated = await backup.InvalidateAsync(datasetId, ct);   // 4. 백업 키 폐기 / 서버 사본 삭제
        await registry.NotifyDatasetDeletedAsync(datasetId, ct);                   // 5. (해당 시) 동의 레코드 상태 갱신
        report.Residuals = ResidualScanner.Scan(datasetId, paths);                 // 6. 잔존물 스캔(파일명·ID 기준)
        await audit.RecordAsync(AuditEvent.DatasetDeleted(datasetId, report.Summary), ct);   // 7. 내용 없는 감사 기록
        return report;
    }

    private static bool BestEffortDelete(string path)
    {
        try { if (File.Exists(path)) File.Delete(path); else if (Directory.Exists(path)) Directory.Delete(path, true); return true; }
        catch (IOException) { return false; }   // 잠김 → 재부팅 후 삭제 예약(MoveFileEx DELAY_UNTIL_REBOOT)
    }
}
```

- **B**: 근로자 동의의 자발성, 퇴사 후 사용, 상담 기록 속 고객 개인정보 목적 외 이용이 문제입니다. → **E로 대체**합니다.
- **C**: 법적으로 가장 안전하고 기술 검증에 최적입니다. 하지만 **카톡에 직접 붙일 수 없는 PC 앱이라 사용 마찰이 있고**, 카카오(카나나 인 카카오톡, 온디바이스 대화 분석)나 삼성 같은 **플랫폼 기본 기능과 경쟁**합니다. 단독 유료 BM으로는 약합니다. → **H와 묶어 초기 트래픽·검증용**으로 씁니다.
- **D**: 본인 동의·계약이 명확합니다. 다만 데이터 원천이 카톡보다는 강의·영상·글이어서 이 제품의 강점(카톡 파서)과 덜 맞고, 해외 경쟁(Delphi 등)이 강합니다. 퍼블리시티 계약이 필요합니다.
- **E**: 고객사가 데이터 처리자이고, 온프레미스 수요가 있으며, 교육·품질관리 ROI를 설명할 수 있습니다. 다수 상담원 집계로 특정인 복제 문제를 피할 수 있습니다. 상담 로그 속 고객정보는 **가명처리 + 고객사 처리 근거**로 해결합니다. **지불 의향이 가장 높습니다.**
- **F**: Memorial을 합법화하는 유일한 경로입니다. 다만 "언젠가 쓸 것"에 지금 돈을 내는 수요는 작습니다. 상조·보험·장례 B2B2C 제휴가 필요합니다.
- **G**: 가족 전원의 동의를 받는 UX가 어렵지만 정서적 가치가 크고, F의 전 단계로 좋습니다.
- **H**: 분석만 하므로 Persona 위험이 없습니다. 다만 **타인 감정 추적은 감시 도구화(연인·자녀 감시)** 위험이 있어 본인 중심으로 설계해야 합니다.
- **I**: E의 엔진을 제품화한 것입니다. 초기 단독 판매는 어렵고 E 레퍼런스 확보 후에 진행합니다.

**초기 진입 전략**
1. **B2C 웨지(0~4개월)**: H + C 로컬 앱을 일회성 구매/연 구독으로 출시합니다. 목적은 매출보다 **파서·프라이버시·스타일·검색 엔진 검증과 브랜드 신뢰**입니다.
2. **B2B 매출(3~9개월)**: E PoC 2~3건(콜센터, 보험·통신 CS, 영업 조직). 온프레미스·폐쇄망으로 진행합니다.
3. **동의 인프라(6~12개월)**: Consent Registry → 동의 기반 상대 Persona(G) → Digital Legacy(F) → 동의 있는 Memorial.

### 15.3 Local First인데 구독 매출을 만드는 방법
1. **형식 호환성 보장 구독**: 메신저 앱 업데이트로 내보내기 형식이 바뀌면 즉시 어댑터를 배포합니다(서명된 규칙 업데이트). 실제로 반복해서 생기는 가치입니다.
2. **모델·품질 업데이트**: 새 Apache 모델 검증 프로필, 프롬프트·Grounding 개선.
3. **E2E 암호화 백업·기기 이전**: 회사가 복호화할 수 없는 구조(키는 사용자). 단, 이 경우에도 개인정보 처리 해당 여부는 **[법률 검토 필요]**입니다.
4. **연간 리포트 / 기념일 리포트**(로컬 생성): "우리의 1년" 같은 정서적 반복 구매 포인트.
5. **Legacy·Family 플랜**: 동의 레지스트리, 수령인 관리, 기간 관리는 본질적으로 서버 기능이어서 구독 정당성이 있습니다.
6. B2B 유지보수·Seat.

## 16. Digital Memorial 별도 분석

### 16.1 법률
- 3.10의 구조 비교 결론을 따릅니다. **생전 Legacy Consent + 수령인 본인 참여 대화만 + 상대방 정보 최소화 + 유족 이의 절차**가 가장 방어력이 높습니다.
- 추가 쟁점:
  - (a) 수령인 지정의 법적 성질(유언과의 관계, 유언 방식 요건 불충족 시 효력) **[법률 검토 필요]**
  - (b) 상속인과 수령인이 다를 때의 충돌
  - (c) 고인 단말 접근 금지(3.7)
  - (d) 사자 명예훼손(허위 생성)
  - (e) 미성년 유족 이용
- 해외 진출 시 캘리포니아 SB 243, 중국 의인화 AI 잠정조치(상시 AI 표시, 2시간 초과 이용 알림, 미성년자 보호)를 따라야 합니다 [S24].

### 16.2 윤리
- 케임브리지대 LCFI 연구(Hollanek & Nowaczyk-Basińska, 2024)는 griefbot 위험으로 다음을 지적하고, **데이터 제공자(고인)와 이용자(유족)의 동의 분리, 연령 제한, "은퇴(retirement)" 절차, 의미 있는 투명성**을 권고했습니다 [S25].
  - ① 고인을 광고·판매 수단으로 이용
  - ② 원치 않는 "디지털 출몰(haunting)"
  - ③ 이용 중단의 어려움
- 상업적 이해와 애도 지원의 충돌을 경계해야 합니다. **이용 시간을 늘리는 것을 KPI로 삼으면 안 됩니다.**

### 16.3 제안된 안전장치 평가와 추가안
| 안전장치 | 평가 | 보강 |

| **추가: 위기 대응** | 필수 | 자해·자살 신호 감지 시 Persona 화법을 중단하고 상담 안내(자살예방 상담전화 109) |
| **추가: 사용량 알림** | 권고 | 1회 60분, 일 2시간 초과 알림. 야간(0~5시) 지속 사용 알림 |
| **추가: 기념일 자동 메시지 금지** | 권고 | Persona가 먼저 말 걸기(푸시) 금지. 고인이 먼저 연락하는 경험은 해로울 수 있음 |

| **추가: 음성·영상 금지(초기)** | 필수 | 딥페이크 표시 의무와 정서적 충격 때문에 텍스트 한정 |

### 16.4 UX 흐름(동의 있는 Memorial)
`생전: Legacy 문서 작성(본인 인증) → 수령인 초대·수락 → 사망 통지(가족관계증명서 + 2인 확인) → 수령인이 자기 단말 대화 Import → 범위 확인(문서 기준) → 대기기간(예: 사망 후 30일, 즉시 생성 방지) → Persona 생성 → 상시 표시·사용량 알림 → 만료/은퇴`

## 20. 최종 제품 Concept

### 20.1 제품 컨셉 (MVP1~2 기준)
- **한 문장 소개**: 수년간의 메신저 대화를 내 PC 안에서만 분석해, 나의 말투와 우리의 기억을 근거와 함께 되살려 주는 프라이버시 우선 AI.
- **핵심 고객**: ① 대화 기록이 많은 20~40대(관계·기억·자기 이해에 관심), ② 개인정보에 민감해 클라우드 AI를 꺼리는 사용자, ③ (B2B) 상담 품질·신입 교육이 필요한 CS·영업 조직.
- **핵심 기능**: 대화 분석 리포트, 내 말투 답장 초안, 근거 기반 기억 검색, 동의한 사람만 Persona, 원클릭 완전 삭제.
- **핵심 차별점**: 원문이 외부로 나가지 않는 구조 + 참여자별 동의 + 기억을 지어내지 않는(근거 표시) Persona.

## 21. 법률사무소에 의뢰해야 할 쟁점 (우선순위 순)

1. **Local-only 구조에서 회사의 개인정보처리자 해당 여부**(설치형 소프트웨어 공급자, 모델 업데이트·라이선스 서버만 운영할 때)와 사용자 개인의 '업무 목적' 해당성
2. **BYOK Cloud 모드**에서 회사가 국외이전·처리위탁 주체가 되는지
3. **상대방(미동의 참여자) 발화를 로컬에서 맥락으로만 처리**하는 설계의 적법성과 회사의 설계 책임(민사 방조 포함)
4. **동의 레지스트리** 운영 시 상대방 동의의 유효 요건(본인 확인 수준, 고지 항목, 민감정보 별도 동의, 철회 효과의 기술적 이행)
5. 카카오 서비스 약관의 "다른 이용자 정보 무단 수집·이용·제공", "영리 목적 이용" 조항이 **제3자 소프트웨어로 내보내기 파일을 처리하는 행위**에 미치는지, 카카오의 제재·청구 가능성
6. AI 기본법 제31조: 로컬 실행 소프트웨어에서의 '인공지능사업자' 해당성, **Self Persona 초안이 앱 밖으로 복사될 때 표시 의무 범위**
7. **고인 Persona**: Legacy Consent의 법적 성질(유언과의 관계), 상속인·수령인 충돌, 유족의 고인 단말 접근과 정보통신망법 제49조·형법 제316조
8. 사자 명예훼손·유족 인격권 침해 소송 위험과 면책 약관의 유효성
9. B2B(E): 상담 기록의 교육용 AI 활용이 제15조 제3항 추가적 이용, 가명정보 과학적 연구, 2027-03-09 시행 AI 특례 중 어디에 해당하는지, 상담원 동의의 자발성
10. 모델 라이선스: Kanana-2 Open License 4.1(iii) "on-device" 해당성, HyperCLOVA X SEED 경쟁 조항, Gemma Terms(임베딩) 패스스루 의무
11. 메신저 피싱 악용 시 회사 책임과 필요한 주의의무 수준
12. 전자상거래·환불(디지털 콘텐츠 청약철회 제한 고지), 전기통신사업법상 부가통신사업 신고 필요 여부(동의 레지스트리·백업 서버 운영 시)

5. **Self Style Profile + "내 말투 답장 초안"**(Exemplar 검색 + 자연어 스타일 규칙 + 후처리, 자동 발송 없음)
6. **근거 기반 Memory 검색**(Persona 화법 없이 원문 카드로 답)
7. **Vault 보안**(데이터셋별 SQLCipher, DPAPI KEK, crypto-shredding 전체 삭제, 텔레메트리 없음)
8. **AI 기본법 고지·표시**, 처리방침에 "원문 외부 전송 없음" 명시와 실제 구현 일치

### 23.3 Local AI와 Cloud AI를 어떻게 나눌 것인가
| 처리 | 위치 | 비고 |
|---|---|---|
| 파싱, PII 탐지, 세션 분할, 임베딩, 검색, 스타일 분석, 감정 주석, 생성, Grounding 검증 | **Local(필수)** | 원문·벡터·프롬프트는 PC 밖으로 나가지 않음 |
| 고품질 생성(옵션) | **BYOK Cloud** — 사용자 키로 PC에서 직접 호출 | 본인 발화 + 마스킹된 최소 맥락만. 상대방 원문·민감정보·QUOTE 원문 전송 금지. 기능 단위 옵트인, 매 세션 표시 |
| 계정, 결제, 라이선스 | Company Cloud | 대화 데이터 없음 |
| 동의 레지스트리(MVP2~) | Company Cloud | consentId·범위·만료·철회·본인확인 해시만 |
| 업데이트·모델 허용목록·파서 규칙 | Company Cloud → 서명 배포 | 공급망 보안 |
| 백업(MVP3~) | E2E 암호화(회사 복호화 불가) | 법률 검토 후 |

### 23.4 어떤 BM부터 검증할 것인가
1. **H + C(로컬 B2C)** — 3개월차 베타. 검증 지표는 Free→Pro 전환율 ≥ 3%, 주간 재방문, "내 말투 초안" 사용 빈도, 파서 실패율. 목적은 **엔진 검증과 신뢰 확보**이고, 큰 매출을 기대하지 않습니다.
2. **E(B2B 표준 상담 Persona, 온프레미스)** — 3개월차부터 고객 인터뷰 15곳, 5~6개월차 PoC 1~2건. 검증 지표는 신입 상담원 교육 기간 단축률, QA 점수, PoC→본계약 전환. **실제 매출의 1순위 후보**입니다.
3. **G → F(동의 기반 가족 Persona → Digital Legacy)** — 6개월차 이후 Consent Registry가 검증되면 시작합니다. 상조·보험 제휴로 B2B2C 실험을 합니다.
4. **A(동의 없는 Memorial), B(직원 1인 복제)** — 검증하지 않습니다.

> **최종 판단**: "카톡으로 고인을 되살리는 AI"는 이야기로는 가장 강력하지만, 지금 출시하면 회사를 가장 빨리 위험하게 만드는 제품입니다. 같은 엔진을 **본인 데이터(C/H) → 동의 인프라(Registry) → B2B(E) → 동의 있는 Memorial(F)** 순서로 쌓는 것이 기술적으로 가능하고 법적으로도 상용화할 수 있는 경로입니다.
